# korean-writing

> AI 티 나는 한국어를 자연스러운 한국어로. 장르마다 다르게.

한국어 텍스트를 받아 AI 안티패턴을 제거하고, **장르에 맞는 구조와 톤으로** 다시 쓰는 스킬.
원작자의 의도와 톤은 유지하고, 부자연스러운 표면만 다듬는다.

---

## 핵심 원칙 (공통)

다음 다섯 가지를 모든 장르에서 동시에 만족시킨다.

1. **AI 안티패턴 0건.** Em dash, 빈 강조어, 클리셰, 영어 calque, 가정형 모두 제거.
2. **한 문장 한 의미.** 긴 복문을 짧은 단문으로 분리.
3. **추상을 구체로.** 모호한 표현을 숫자, 명사, 행동으로 변환.
4. **목소리 보존.** 원작자의 톤과 단어 선택을 존중. 표면만 다듬음.
5. **MECE 구조.** 중복 없이, 빠짐없이. 한 단락 한 메시지.

---

## 9가지 장르

장르마다 핵심 구조, 톤, 길이가 다르다. 각 장르 전용 references 파일을 참조한다.

| 장르 | 무엇을 위한 글 | 참고 파일 |
|---|---|---|
| **blog** | 블로그/에세이 (깊은 인사이트) | `references/genre-blog.md` |
| **linkedin** | 링크드인 포스트 (중간 길이 인사이트) | `references/genre-linkedin.md` |
| **business-comm** | 업무 이메일/메시지 | `references/genre-business-comm.md` |
| **gov-doc** | 거버넌스 문서 (제안서, 정책, 의사결정) | `references/genre-gov-doc.md` |
| **announcement** | 공지/모집 (디스코드, 마케팅) | `references/genre-announcement.md` |
| **feedback** | 피드백/리뷰 (자료에 대한 응답) | `references/genre-feedback.md` |
| **report** | 기술/리포트 (PRD, 분석 보고서) | `references/genre-report.md` |
| **ui-ux** | UI/UX 라이팅 (버튼, 에러, 토스트, 온보딩) | `references/genre-ui-ux.md` |
| **tech-doc** | 테크니컬 라이팅 (API·튜토리얼·How-To·참조·설명·ADR·README) | `references/genre-tech-doc.md` |

## 워크플로우 (7단계)

```
① INTAKE     원문 받기 + 컨텍스트 확인
② AUDIT      공통 안티패턴 자동 검출
③ CLASSIFY   글 장르 분류
④ LOAD       해당 장르 references 파일 로드
⑤ REWRITE    공통 룰 + 장르 룰 동시 적용
⑥ VERIFY     공통 + 장르 체크리스트 통과 확인
⑦ PRESENT    Before/After + 변경 요약
```

---

### ① INTAKE. 원문 받기

원문이 주어지면 다음 3가지를 확인한다. 부족하면 묻는다.

1. **원문의 출처.** 직접 쓴 글인지, AI가 쓴 글인지, 번역인지.
2. **사용 목적.** 어디에 올릴/보낼 글인지.
3. **유지해야 할 톤.** 격식 있게, 친근하게, 단호하게 등.

목적 정보가 없으면 원문에서 추론하되, 추측이 크면 사용자에게 확인한다.

---

### ② AUDIT. 공통 안티패턴 자동 검출

`references/anti-patterns.md` 의 10개 카테고리를 적용해 검출한다.

검출 결과는 카운트와 위치까지 기록한다. ⑦ PRESENT에서 사용.

---

### ③ CLASSIFY. 글 장르 분류

다음 신호를 보고 9가지 중 하나로 분류한다.

| 분류 신호 | 장르 |
|---|---|
| 본인 인사이트, 분석, 경험 공유. 1,500자 이상. | blog |
| 짧은 회고나 인사이트. 후킹 첫 줄. 800-2,000자. | linkedin |
| "안녕하세요", "회신 부탁드립니다" 등. 격식. 짧음. | business-comm |
| "제안", "정책", "의사결정", "권장사항" 등 구조어. 길고 격식. | gov-doc |
| "출시", "모집", "공지", CTA 명확. 짧고 후킹. | announcement |
| 자료/질문에 대한 응답. 진단과 행동 포함. | feedback |
| "분석 결과", "Q1 보고", 수치 중심. 구조화. | report |
| 버튼, 에러 메시지, 토스트, 툴팁, 빈 상태, 온보딩 문구. 짧고 행동 중심. | ui-ux |
| API 명세, 튜토리얼, How-To, 트러블슈팅, ADR, 개발자 README, 개념·아키텍처 설명. 독자 = 개발자. 코드 블록·절차·식별자 포함. | tech-doc |

분류가 애매하면 가장 강한 신호를 따른다.
분류가 끝나면 사용자에게 분류 결과를 알리고 진행한다.

---

### ④ LOAD. 장르 references 파일 로드

분류된 장르에 해당하는 `references/genre-{장르}.md` 를 읽는다.
각 장르 파일은 다음을 포함한다.

- **정의**. 이 장르가 무엇인지.
- **핵심 구조**. 어떤 순서로 써야 하는지.
- **톤 / 길이 / 종결어**. 가이드.
- **장르 특수 안티패턴**. 공통 외에 이 장르에서 특히 조심할 것.
- **Before / After 예시**.
- **장르 체크리스트**.

---

### ⑤ REWRITE. 공통 룰 + 장르 룰 적용

**공통 작업 (모든 장르 동일)**

| 패턴 | 변환 방식 |
|---|---|
| Em dash | 마침표, 쉼표, 콜론으로 대체 |
| 빈 강조어 | 삭제 또는 구체적 수치로 대체 |
| 클리셰 동사 | 구체적 행동 동사로 대체 |
| 가정형 | 사실 또는 가능성으로 변환 |
| 영어 calque | 자연스러운 한국어로 대체 또는 삭제 |
| 빈 호칭 | 삭제 또는 구체적 호명으로 대체 |
| 본문 이모지 | 삭제 (장르에 따라 일부 허용) |
| 복문 과다 | 짧은 단문으로 분리 |

**장르별 작업**
④에서 로드한 장르 파일의 핵심 구조와 톤을 적용한다.

**리듬 작업**
- 4절 이상 복문을 짧은 단문 2-3개로 분리.
- 한 단락은 3-5 문장. 6 문장 넘기지 않음.
- 종결어 변화 (장르 파일의 종결어 풀 안에서).

**구체성 작업**
- 모호한 표현을 숫자, 고유명사, 행동으로 대체.

**목소리 보존**
- 원작자가 즐겨 쓰는 단어는 그대로.
- 톤의 강도(격식, 친근함, 단호함)는 원본을 따른다.
- 표면 표현만 다듬는다. 의도와 결론은 바꾸지 않는다.

---

### ⑥ VERIFY. 공통 + 장르 체크리스트

리라이팅 완료 후, 두 가지를 확인한다.

**공통 체크리스트 (모든 장르)**

- [ ] Em dash 0건
- [ ] 빈 호칭 0건 (인용 제외)
- [ ] 빈 강조어 0건
- [ ] 클리셰 0건
- [ ] 가정형 0건
- [ ] 영어 calque 0건
- [ ] 6 문장 넘는 단락 0개

**장르 체크리스트**
④에서 로드한 장르 파일의 체크리스트를 적용.

하나라도 통과 못 하면 ⑤로 돌아간다.

---

### ⑦ PRESENT. Before/After + 변경 요약

다음 형식으로 사용자에게 제시한다.

```markdown
## 리라이팅 완료

**장르**: [분류된 장르]
**검출된 안티패턴**:
- Em dash N건
- 빈 강조어 N건
- 클리셰 N건
- (기타)

### Before
(원문)

### After
(리라이팅된 글)

### 주요 변경 사항
- [변경 1: 무엇을 어떻게 바꿨는지]
- [변경 2]
- [변경 3]

### 장르 특수 조정
- [이 장르 기준으로 추가 조정한 부분]
```

원문이 길면 핵심 변경 부분만 강조해서 보여준다.

## 무엇을 하지 않는가

- 원작자의 의도를 바꾸지 않는다. 표면 표현만 다듬는다.
- 사실 정보를 추가하거나 빼지 않는다.
- 원본에 없는 새로운 주장이나 결론을 만들지 않는다.
- 모호한 부분이 있으면 추측하지 않는다. 사용자에게 묻는다.
- 장르를 무작정 추측하지 않는다. 신호가 약하면 사용자에게 확인한다.
