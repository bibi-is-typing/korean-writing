# 장르: tech-doc (테크니컬 라이팅)

API 문서, 튜토리얼, How-To 가이드, 트러블슈팅, 개념 설명서, ADR(아키텍처 결정 기록), 명세서, 개발자 README.
독자가 **개발자**이고, 목적이 **시스템·기술·도구를 이해하거나 사용하는 것**인 모든 문서.

근거 가이드: [toss/technical-writing](https://technical-writing.dev/) (한국 토스 팀 공식 가이드).

---

## 정의

다음 중 하나에 해당하면 tech-doc 장르.

- **API 명세**. 엔드포인트·파라미터·반환값·예시 코드.
- **튜토리얼**. 처음 접하는 개발자를 위한 단계별 학습.
- **How-To 가이드**. 특정 문제 해결 절차.
- **트러블슈팅**. 에러·예외 상황 진단·복구.
- **개념·아키텍처 설명**. 왜 이 기술이 존재하는가, 어떻게 동작하는가.
- **ADR / 설계 문서**. 결정과 트레이드오프 기록 (gov-doc 와 겹치면 gov-doc 우선).
- **개발자 README**. 라이브러리·서비스 입문 문서.

핵심 특징: **독자는 능동적으로 작업을 수행할 개발자**. "읽고 끝"이 아니라 "읽고 따라 한다".

## 4가지 하위 유형 (분기)

문서 유형이 다르면 구조도 다르다. 작업 시작 전 어느 유형인지 분류.

### ① 학습 중심 (Learning)

처음 접하는 개발자가 흐름을 파악하기 위한 문서. *튜토리얼*.

```
1. 무엇을 배우는가 (목표 한 줄)
2. 전제 조건 (사전 지식·환경 요구)
3. 단계별 실습 (1, 2, 3...)
4. 각 단계 결과 확인 방법
5. 마지막에 만든 것 요약
6. 다음 단계 (참조 문서 링크)
```

### ② 문제 해결 (Problem-Solving / How-To)

배경 지식이 있는 개발자가 특정 작업을 끝내기 위한 문서. *How-To*.

```
1. 어떤 문제를 해결하는가
2. 전제 (어떤 상태에서 시작)
3. 해결 절차
4. 검증 방법
5. 자주 발생하는 실패 케이스
```

### ③ 참조 (Reference)

기능·API 사용법을 정확히 확인하기 위한 문서. *Spec*.

```
1. 식별자 (함수·엔드포인트·옵션 이름)
2. 시그니처 (파라미터·타입·반환값)
3. 동작 설명
4. 예시 코드 (입력·출력)
5. 에러·예외 케이스
6. 관련 항목 링크
```

### ④ 설명 (Explanation)

개념·원리·배경을 깊이 이해하기 위한 문서.

```
1. 이 개념이 왜 존재하는가
2. 어떤 문제를 푸는가
3. 대안과의 비교
4. 동작 원리
5. 한계와 트레이드오프
```

→ 한 문서가 여러 유형을 섞을 수 있지만 (예: 학습 + 설명), 주된 유형은 하나로 정한다.

## 톤 / 길이 / 종결어

| 항목 | 가이드 |
|---|---|
| 전체 길이 | 한 문서 한 주제. 헤딩 깊이가 H4 (`####`) 이상 가면 분리 고려 |
| 한 단락 | 3-5 문장 |
| 종결어 | `~다 / ~한다 / ~하세요` (유형에 따라). 튜토리얼·How-To는 `~하세요` 자연스러움 |
| 톤 | 단정적, 능동, 친절. 메타 담화 최소 |
| 인칭 | 독자(개발자)를 주체로. 시스템·라이브러리를 주어로 쓰지 않음 |
| 코드 | 실행 가능한 완성 코드. 발췌·... 생략 지양 |
| 헤딩 | 핵심 키워드 포함, 30자 이내, 선언형 |

## 장르 특수 안티패턴

공통 안티패턴 외에 tech-doc 에서 특히 조심할 것.

| 패턴 | 왜 금지 | 대체 |
|---|---|---|
| 도구·시스템을 주어로 | "이 라이브러리는 ~을 수행해요" → 독자가 무엇을 할지 안 보임 | 독자(개발자)를 주어로 |
| 수동태 | "설정이 완료되어야 합니다" | "설정을 완료하세요" |
| `~을 수행하다 / 실시하다 / 진행하다` | 명사화 + 한자어 동사가 의미를 흐림 | 동사 직접 사용 (`삭제하다`) |
| `~을 통해`, `~함으로써` | 영어 calque, 명사화 | 한국어 동사로 직역 |
| 모호한 표현 | "많을 때", "빠르게", "성능 저하" | 숫자·기준 (`10,000건 넘으면`, `1초 이상`) |
| 약어 정의 없이 사용 | 신규 독자가 못 읽음 | 첫 사용 시 `SSR(Server-Side Rendering)` 정의 |
| 한 단어 여러 표현 | "추가/첨부/넣다" 섞어 쓰면 같은 개념인지 혼란 | 한 개념 한 단어 통일 |
| 개요·요약 부재 | 독자가 문서 가치를 빨리 못 잡음 | 첫 단락에 핵심 요약 |
| 추측·hedge 과다 | "~할 수도 있어요" 가 정보 신뢰 깎음 | 단정형 또는 조건부 사실 |
| 비공식 약칭 | "K8" | 공식 표기 `쿠버네티스(Kubernetes)` |

## 핵심 작성 원칙 (3 Pillars × 토스 가이드)

### Pillar 1. 문서 유형부터 정한다

같은 주제라도 유형이 다르면 구조가 다르다. 시작 전 어떤 유형인지 확정.

❌ 튜토리얼·참조·설명을 한 페이지에 다 우겨넣기.
✅ 학습용은 학습용. 참조는 참조. 한 유형 = 한 페이지.

### Pillar 2. 정보 구조를 독자 관점에서 짠다

**원칙 1: 한 페이지 한 주제**
H4(`####`) 이상 깊이로 가면 별 문서로 분리. 분리된 문서는 *개요 페이지*로 연결.

**원칙 2: 가치 먼저, 비용 나중**
독자가 얻는 것(가치) 부터 보여주고, 절차·요구·세부는 그 다음.

❌ "이 기능을 사용하려면 A·B·C 설정이 필요합니다. (4문단 뒤) 그러면 X를 할 수 있어요."
✅ "이 기능으로 X를 자동화할 수 있습니다. 사용하려면 A·B·C 설정이 필요합니다."

**원칙 3: 효과적인 헤딩**
- 핵심 키워드 포함
- 30자 이내
- 선언형 (`~하는 법`, `~의 동작`)

❌ "여러분이 시작하기 위해 알아야 할 모든 것을 다루는 시작 가이드"
✅ "시작 가이드"

**원칙 4: 개요 빠트리지 않기**
문서 첫 단락에 *핵심 내용을 요약*. 독자가 0.5초 안에 가치 판단 가능.

**원칙 5: 예측 가능하게 하기**
같은 유형 문서끼리 *제목·형식·구조 통일*. 한 문서를 본 독자가 다음 문서 구조를 예측 가능.

**원칙 6: 새 개념은 자세히 설명**
용어를 처음 등장시킬 때 정의·예시. 약어는 첫 사용 시 풀어쓰기.

### Pillar 3. 문장을 다듬는다

**원칙 1: 주어를 명확히 — 독자를 주체로**

❌ "이 라이브러리는 데이터베이스 초기화를 수행해요."
✅ "이 명령어를 실행하면 데이터베이스를 초기화할 수 있어요."

❌ "애플리케이션이 실행되기 전에 설정이 완료되어야 합니다."
✅ "애플리케이션을 실행하기 전에 설정을 완료하세요."

**원칙 2: 간결성 — 한 문장 한 의미**

❌ "버튼을 클릭하면 다음 단계로 이동하게 되며, 그 이후의 작업을 진행할 수 있습니다."
✅ "버튼을 클릭하면 다음 단계로 이동합니다. 이동 후 이어서 작업을 진행하세요."

❌ "이 API를 호출할 때 요청 헤더를 포함해야 하며, 올바른 인증 정보를 제공해야 정상적으로 응답을 받을 수 있습니다."
✅ "이 API를 호출할 때 요청 헤더와 인증 정보를 포함하세요."

**원칙 3: 구체성 — 숫자·기준으로**

❌ "데이터가 많을 때는 성능이 저하될 수 있습니다."
✅ "데이터가 10,000건을 넘으면 응답 시간이 1초 이상 걸립니다."

❌ "요청량이 많으면 응답 시간이 느려질 수 있습니다."
✅ "초당 요청량이 1,000건을 넘기면 API 응답 시간이 2초 이상 증가할 수 있습니다."

❌ "파일 크기가 클 때는 업로드에 시간이 걸립니다."
✅ "파일 크기가 100MB를 넘기면 업로드에 최소 30초 이상 걸릴 수 있습니다."

**원칙 4: 자연스러운 한국어 — 명사화 제거**

❌ "로그 파일을 삭제하는 작업을 수행합니다"
✅ "로그 파일을 삭제합니다"

❌ "API 키를 이용한 사용자 인증 처리가 완료된 후, 데이터베이스 접속 설정 진행이 가능합니다"
✅ "API 키로 사용자를 인증한 후, 데이터베이스에 접속하도록 설정할 수 있습니다"

❌ "시스템 모니터링 수행을 통해 서버 성능 측정 작업을 실시하게 됩니다"
✅ "시스템을 모니터링해서 서버 성능을 측정합니다"

❌ "보안 정책 업데이트 진행 후 시스템 재시작 처리를 수행해야 합니다"
✅ "보안 정책을 업데이트한 후 시스템을 재시작합니다"

**제거 대상 동사**: 수행하다, 실시하다, 진행하다, 처리하다.
**제거 대상 명사화**: `~을 통해`, `~함으로써`, `~의 진행`, `~의 처리`.

**원칙 5: 일관성 — 공식 용어·한 개념 한 단어**

❌ "K8을 사용하면 ..."
✅ "쿠버네티스(Kubernetes)를 사용하면 ..."

❌ "파일을 추가하려면... 파일을 첨부한 후... 파일을 다시 넣을 수 있습니다." *(추가/첨부/넣다 혼용)*
✅ "파일을 업로드하려면... 파일을 업로드한 후... 파일을 다시 업로드할 수 있습니다."

❌ "이 기능은 SSR을 지원합니다."
✅ "이 기능은 SSR(Server-Side Rendering)을 지원합니다."

❌ "프런트엔드"
✅ "프론트엔드" *(공식 외래어 표기)*

## Before / After (전체 흐름)

### Before (How-To 문서)

```
Redis 설정에 관한 가이드

기본적으로 본 문서는 Redis 설정 관련 정보를 제공하기 위한 목적으로 작성되었습니다. 
Redis는 다양한 용도로 활용 가능한 인메모리 데이터 저장소이며, 본질적으로 캐싱 등에서 
많이 사용됩니다. 설정을 진행하기 위해서는 먼저 설치가 완료되어야 하며, 그 이후에 
설정 파일의 수정 작업을 수행해야 합니다. 메모리 사용량이 많을 때는 성능에 영향이 
있을 수 있으므로, 적절한 설정이 필요합니다.
```

### After

```
# Redis 메모리 한도를 설정하기

Redis 메모리 사용량을 제한해 OOM(Out Of Memory) 에러를 막는 방법.

## 전제

- Redis 7.0 이상 설치
- `redis.conf` 파일 접근 권한

## 절차

1. `redis.conf` 파일을 엽니다.
2. `maxmemory` 옵션에 한도를 지정합니다. 예: `maxmemory 2gb`.
3. `maxmemory-policy` 옵션으로 한도 초과 시 정책을 정합니다. 예: `allkeys-lru`.
4. Redis 를 재시작합니다: `sudo systemctl restart redis`.
5. `redis-cli` 로 적용을 확인합니다: `CONFIG GET maxmemory`.

## 주의

데이터셋이 2GB를 넘으면 LRU(Least Recently Used) 정책에 따라 오래된 키부터 자동 삭제됩니다. 
영구 저장이 필요한 데이터는 `noeviction` 정책을 사용하고, 별도의 영구 저장소를 함께 운영하세요.

## 관련 문서

- Redis Eviction 정책 (참조)
- Redis 영구 저장 설정 (How-To)
```

변경 요약:
- 헤딩 `Redis 메모리 한도를 설정하기` — 30자 이내, 핵심 키워드, 선언형
- 개요 한 줄 — 가치(OOM 막기) 먼저
- 전제 명시 — 독자가 시작 가능한지 즉시 판단
- 절차 능동 명령형 — 독자가 주체
- 모호 표현 → 구체 (`2gb`, `LRU`, `최대 메모리 한도`)
- 명사화 제거 (`설정 진행`, `수정 작업 수행` 삭제)
- 약어 풀기 (`OOM`, `LRU`)
- 관련 문서 링크 — 예측 가능 구조
